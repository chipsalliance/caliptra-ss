# Full-Speed (FS) Link Test

**Testcase:** `caliptra_ss_usb_fs_clock`

## Overview

Verifies that the USB device controller behind the compound hub links up and
actually runs at Full Speed (12 Mbit/s) rather than High Speed.

The test name is historical. There is deliberately no clock-frequency check:
see "Why there is no clock check" below.

## Operation

1. The UVM test sets `high_speed_capable = 0` in the SVT VIP host cfg, so the
   host never offers HS chirp.
2. MCU firmware calls `boot_usb_core_fs()`, which
   - performs hub bring-up phase 1 (programs and validates the HUB descriptor
     RAM, sets `HUB_EN`), and
   - programs USBDC0 with `DEVCMDSTAT.PFSC` set so the device controller does
     not emit K-chirp and does not stall ~2.2 ms waiting for a J-chirp reply
     that an FS-only host never sends.
3. Firmware calls `usb_hub_connect()` (phase 2, `HUB_CONNECT`) once USBDC0 is
   fully programmed, so the upstream host can see the hub.
4. The host sequence waits for the link to reach `ENABLED` (bounded by
   `link_up_timeout_us`, which raises a `uvm_error` on expiry), starts SOF
   generation, and holds an observation window.
5. Firmware idles servicing bus resets, then halts via `csr_write_mpmc_halt()`.

## What Is Verified

Enforced by `caliptra_ss_usb_fs_speed_checker.sv` (testbench-side, enabled by
the `+usb_fs_speed_check` plusarg from this test's `.yml`):

| Check | Meaning |
|-------|---------|
| `CHK_XCVR_FS` | On the first received byte, the PHY speed-select pins are at their FS values (`xcvrselect = 1`, `termselect = 1`). |
| `CHK_RATE_FS` | The measured UTMI RXValid byte period is within 600-740 ns, i.e. 12 Mbit/s. HS would give about 16.7 ns. Measured in simulation time, not clock counts, so it does not depend on the UTMI clock frequency. |
| `CHK_SOF_PERIOD` | Optional (`+usb_fs_sof_check`): SOF interval is within 900-1100 us, the FS frame period. |
| `CHK_SAW_TRAFFIC` | By the time the host sequence closes its observation window, at least one packet was received AND `CHK_RATE_FS` reached a verdict, so neither a silent link nor an unevaluated check can pass vacuously. |


Enforced elsewhere:

- Link reaches `ENABLED` within `link_up_timeout_us` (host sequence).
- Firmware reaches `csr_write_mpmc_halt()` within the MCU-halt timeout
  (`caliptra_ss_usb_base_test`), and no `UVM_ERROR`/`UVM_FATAL` was reported.

## Checker validation (non-vacuity)

A check that never fails proves nothing, so the checker was run a second time
against a High Speed link by enabling it on an HS test. Both speed checks
failed there, which confirms they actually discriminate FS from HS rather than
passing unconditionally:

| Observable | FS run (this test) | HS run (checker forced on) |
|------------|--------------------|----------------------------|
| `xcvrselect` / `termselect` | 1 / 1 (FS transceiver and termination) | 0 / 0 (HS transceiver and termination) |
| Widest RXValid byte period | 666.688 ns (about 12 Mbit/s) | 16.666 ns (about 480 Mbit/s) |
| `CHK_XCVR_FS` | pass | FAILED, as expected |
| `CHK_RATE_FS` | pass | FAILED, as expected |
| Measured UTMI `CLK` period | 20.834 ns (48 MHz) | 16.666 ns (60 MHz) |
| Verdict | `TESTCASE PASSED` | `TESTCASE FAILED`, as expected |

To reproduce the negative case, add the plusarg to any HS link test:

```
./run_caliptra_test.py -test caliptra_ss_usb_hs_conn -extra_opts +usb_fs_speed_check=1
```

This is a one-off experiment only. Do not leave `+usb_fs_speed_check` enabled
on an HS test in regression: the checker is specific to FS and will correctly
fail the run.


## Why there is no clock check

The link speed cannot be inferred from any clock in this testbench:

- The AST clock generators (`src/ast/rtl/usb_clk.sv`, `usb_osc.sv`,
  `clk_src_usb_o`) are not compiled into `caliptra_ss_top_tb` and the `ast`
  module is never instantiated, so no such net exists.
- The UTMI clock that does exist is generated by the VIP, not by the TB, and is
  not the frequency you might expect. The TB defines
  `USB_UTMI_CLK_PERIOD = 16667ps` (60 MHz) and drives it into the VIP as
  `usb_20_mac_if.utmi_dut_mac_if.clk` (lowercase), but the DUT is clocked from
  `usb_20_mac_if.utmi_dut_mac_if.CLK` (uppercase), which the VIP produces itself
  because the TB asserts `generate_clk = 1'b1`. Measured, that output is
  20.834 ns (48 MHz, the UTMI+ FS-only 8-bit option) on an FS link and 16.666 ns
  (60 MHz) on an HS link, so the VIP does adapt it to the negotiated speed.
- Even so, the clock rate is not a usable speed check: it is an artifact of how
  this VIP chooses to drive the interface, not a property the DUT is required to
  exhibit, and a real 8-bit UTMI+ PHY may run 60 MHz in both modes.


USB speed is carried by the protocol and by the PHY speed-select pins, not by a
clock rate, which is what the checker observes instead. `CHK_RATE_FS` does
measure a rate, but it measures the USB line rate in simulation time via the
RXValid byte period, which is independent of the UTMI clock frequency.

## Run

```
cd $CALIPTRA_WORKSPACE
source caliptra_setup_env.csh
source my_local_env.csh
./run_caliptra_test.py -test caliptra_ss_usb_fs_clock
grep -nE "TESTCASE (PASSED|FAILED)|UVM_ERROR|USB_FS_SPEED_CHK" scratch/vcs_sim.log
```
